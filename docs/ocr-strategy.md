# OCR Strategy: PdfPig vs Amazon Textract

## Context

DocLens processes documents uploaded by tenants — invoices, contracts, reports, and CVs.
Before semantic analysis can run via Amazon Bedrock, raw text must be extracted from those documents.

Two approaches are under consideration: **PdfPig** (direct PDF parsing) and **Amazon Textract** (cloud OCR).

---

## PdfPig

PdfPig is an open-source .NET library that reads the internal structure of a PDF file and extracts text directly — no network call, no ML model, no cost per page.

### How it works

A PDF stores its text as a series of content streams describing where each character is placed on the page. PdfPig reads those streams and reconstructs the text. This only works when the PDF was generated by software (Word export, browser print, digital invoice). If the text was never embedded — because the document was scanned — there is nothing to extract.

### Strengths

- **Zero cost.** No per-page pricing, no API quota.
- **Synchronous.** Result is available immediately in the same Lambda invocation.
- **No external dependency.** Works without network access; suitable for VPC-isolated Lambdas.
- **Fast.** Extraction from a typical 10-page PDF takes single-digit milliseconds.
- **Well-suited for digital documents.** Contracts exported from Word, CVs generated by HR systems, electronic invoices (NF-e, XML-based PDFs) — all work reliably.

### Weaknesses

- **Cannot handle scanned documents.** If the PDF contains only images of pages (e.g., a paper invoice photographed and saved as PDF), PdfPig returns empty or near-empty text.
- **Layout reconstruction is limited.** Tables, multi-column layouts, and rotated text may come out in the wrong order or merged. For structured extraction (invoice line items, contract clauses), this can reduce the quality of Bedrock's semantic analysis.
- **No support for images or Word files natively.** Requires separate handling for `.docx`, `.jpg`, `.png`, etc.

---

## Amazon Textract

Amazon Textract is an AWS managed service that uses machine learning to detect and extract text from document images. It works on scanned PDFs, photographs of documents, and any other image-based input.

### How it works

For multi-page documents, Textract runs as an asynchronous job: `StartDocumentTextDetection` submits the job, and `GetDocumentTextDetection` is polled until the result is ready. For single-page inputs, a synchronous `DetectDocumentText` call is available. Textract also offers `AnalyzeDocument` for structured extraction of tables and key-value form fields.

### Strengths

- **Handles scanned documents.** Works on photographs, scanned PDFs, low-resolution images — anything a human can read, Textract can generally parse.
- **Structured data extraction.** `AnalyzeDocument` can return tables and form key-value pairs as structured objects, which is more reliable than asking Bedrock to infer structure from flat text.
- **High accuracy on degraded input.** Skewed pages, uneven lighting, mixed fonts — Textract is trained on a wide variety of real-world document quality.
- **AWS-native.** Integrates directly with S3; no need to download the file into Lambda memory before processing.

### Weaknesses

- **Cost.** Charged per page. At scale, this becomes significant — especially for multi-page contracts or bulk processing batches.
- **Asynchronous for multi-page documents.** `StartDocumentTextDetection` returns a job ID; the result is not immediately available. This adds latency and requires polling or an SNS/SQS callback, increasing architectural complexity.
- **Cold latency.** Even for single-page synchronous calls, the round-trip to the Textract service adds hundreds of milliseconds compared to in-process extraction.
- **Vendor lock-in.** Textract is AWS-specific. Migrating away requires replacing the OCR layer.
- **Overkill for digital PDFs.** Running OCR on a PDF that already contains embedded text adds cost and latency with no quality gain.

---

## Comparison Summary

| Dimension | PdfPig | Amazon Textract |
|---|---|---|
| Cost | Free | Per-page pricing |
| Latency | Milliseconds (in-process) | Hundreds of ms (sync) / seconds (async job) |
| Scanned documents | No | Yes |
| Digital PDFs | Yes | Yes (redundant) |
| Structured extraction (tables, forms) | Limited | Yes (`AnalyzeDocument`) |
| Async complexity | None | Required for multi-page |
| AWS dependency | None | Yes |
| Cold start impact | None | Network call required |

---

## Recommended Approach: Hybrid Fast Path

Rather than choosing one over the other, the recommended strategy is to use both in a tiered sequence:

1. **Attempt PdfPig first.** Try to extract text directly from the PDF structure.
2. **Evaluate the result.** If the extracted text is below a minimum threshold (e.g., fewer than 50 characters for a document expected to have content), treat the document as image-based.
3. **Fall back to Textract.** Invoke Textract only when PdfPig cannot produce usable text.

This approach keeps the majority of processing fast and free, reserves Textract for cases where it is genuinely needed, and keeps the `IOcrService` interface clean — the calling code does not need to know which path was taken.

### Threshold heuristic

A simple character count is a reasonable starting point. A scanned PDF with no embedded text will yield zero or near-zero characters from PdfPig. A digital PDF with even one page of content will yield hundreds. A threshold between 20 and 100 characters is generally reliable for this distinction.

## Open Questions

- What proportion of uploaded documents are expected to be scanned vs. digital? This directly affects how often Textract will be invoked and the cost projection.
- Should `AnalyzeDocument` (tables/forms) be used instead of `DetectDocumentText` for invoice processing, where structured extraction could improve Bedrock's field accuracy?
- For multi-page documents, should Textract's async job flow be implemented immediately, or deferred until the async processing pipeline (Step Functions / SQS) is in place?
